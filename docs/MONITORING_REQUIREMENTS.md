# Sub2API 监控系统需求文档

- 文档状态：需求草案，作为后续开发计划的输入
- 编写日期：2026-11-14
- 目标技术栈：Prometheus + Grafana + Docker Compose
- 适用环境：本地开发联调环境、远程 Linux 服务器生产环境
- 本文范围：定义目标、功能范围、约束与验收标准；不包含详细开发计划或最终部署配置

## 1. 背景与现状

当前项目已经通过 Docker 部署到远程服务器，并通过宝塔面板管理容器。根据用户提供的截图，现有容器包括：

- `sub2api`：应用，截图中的镜像为 `sun/sub2api:0.0.3`。
- `sub2api-caddy`：反向代理。
- `sub2api-postgres`：PostgreSQL。
- `sub2api-redis`：Redis。

截图显示应用宿主机端口绑定为 `127.0.0.1:8080 -> 8080/tcp`。服务器实际 Compose 文件、Docker 网络、数据卷及 Caddy 网络模式仍需在实施前核对，不能仅凭截图确定。

对当前本地仓库的初步检查表明：

- 应用已有 `/health` 接口，Docker 配置使用该接口进行健康检查。
- 暂未发现现成的 Prometheus `/metrics` 接口或 Prometheus 客户端集成。
- 本地代码检查结果不等同于生产镜像实际内容，实施前需要确认版本一致性。

用户希望监控数据与面板可以持续迭代，因此不采用只在生产服务器手工安装、手工配置看板的方式，而是先在本地完成开发联调，再将监控配置随项目版本一起部署。

## 2. 已明确的用户需求

1. 使用 Prometheus 进行指标采集和存储，使用 Grafana 展示监控面板。
2. 首先在本地开发、调整并联调，验证后再部署到远程服务器。
3. 监控指标、采集配置和面板能够持续迭代。
4. 监控相关代码和配置纳入项目版本管理，支持随项目版本发布。
5. 继续采用 Docker 部署，不因引入监控而迁移到 Kubernetes 等平台。
6. Prometheus 和 Grafana 分别运行在独立容器中。
7. 尽量保留现有应用、数据库、缓存和反向代理部署方式。

下文的一期范围与默认值属于建议基线，尚未明确的产品选择集中记录在第 14 节，供制定开发计划前确认。

## 3. 建设目标

### 3.1 开发目标

- 开发者可以通过文档化命令启动可工作的本地监控环境。
- 本地真实请求能够产生应用指标，并在 Prometheus 和 Grafana 中查询、展示。
- 指标定义、Grafana 看板和 Prometheus 配置变更可以通过 Git 审查与追踪。
- 新环境启动后自动加载数据源和基础看板，不依赖重复手工配置。

### 3.2 运维目标

- 在不推翻现有 Docker 部署的前提下增加监控能力。
- 更新监控配置时，不要求无关业务容器全部重建。
- 重启或升级监控容器后，在保留数据卷的情况下保留历史指标与必要配置。
- 监控故障不得成为业务请求成功处理的前置条件。

### 3.3 可观测性目标

一期首先回答以下问题：

- 应用指标端点是否可被正常采集？
- 应用当前请求量、错误率和响应耗时如何？
- 是否存在异常增多、慢请求增加或并发处理积压？
- 应用进程资源和运行时状态是否出现明显异常？

说明：Prometheus 的 `up` 仅代表采集目标是否成功被抓取，不代表所有业务接口、数据库或上游服务均健康。

## 4. 范围划分

### 4.1 建议一期范围：应用监控闭环

1. Prometheus 和 Grafana 容器化部署。
2. 本地与生产环境的 Compose 组合方式和环境配置。
3. 后端 Prometheus 指标埋点和指标接口。
4. 应用基础运行指标与 HTTP 请求指标。
5. Grafana 数据源和基础看板自动加载。
6. 配置与看板版本化管理。
7. 数据持久化、基础访问控制、资源与保留策略配置。
8. 本地联调、部署、更新、回退及排障说明。

### 4.2 后续扩展范围

以下能力预留扩展空间，但默认不作为一期完成条件：

| 能力 | 候选实现 | 备注 |
| --- | --- | --- |
| 服务器 CPU、内存、磁盘、网络 | Node Exporter | 需在生产 Linux 环境验证 |
| 各容器资源监控 | cAdvisor | 需审查宿主机挂载和权限 |
| PostgreSQL 运行指标 | PostgreSQL Exporter | 需配置监控账号和最小权限 |
| Redis 运行指标 | Redis Exporter | 需配置认证和访问权限 |
| 外部 HTTP 可用性、TLS 等探测 | Blackbox Exporter | 与应用内部健康检查不同 |
| 上游调用耗时、失败与调度状态 | 应用业务埋点 | 需进一步定义业务语义 |
| 告警规则与通知 | Grafana Alerting 或 Alertmanager | 后续确定渠道、阈值和职责 |

### 4.3 非目标

- 不建设完整日志平台或分布式链路追踪平台。
- 不替代项目已有业务统计、账单、审计和管理功能。
- 不通过指标记录请求正文、密钥或用户隐私信息。
- 不要求迁移现有 PostgreSQL、Redis 数据。
- 不要求将本地历史监控数据复制到生产环境。
- 不以多服务器高可用、跨地域监控或长期远程存储为一期目标。
- 不要求一期修改现有业务前端；默认使用独立 Grafana 页面查看监控。

## 5. 总体架构与部署要求

### 5.1 组件关系

- Sub2API 暴露 Prometheus 可读取的指标端点。
- Prometheus 定期通过 HTTP 拉取指标并存储。
- Grafana 通过 Prometheus 数据源查询数据并展示看板。
- 浏览器访问 Grafana，而不是直接连接应用指标端点。

### 5.2 本地环境

建议以完整 Docker 联调作为基线，最小包含五个服务：Sub2API、PostgreSQL、Redis、Prometheus、Grafana。

- 本地默认不要求启动 Caddy，除非需要验证反向代理相关行为。
- 应允许按需不启用监控，避免普通业务开发必须承担全部监控开销。
- 如果后续支持后端直接在宿主机运行，应明确容器访问宿主机应用的配置方式，不与容器化基线混淆。
- 本地为 macOS 时，Docker 运行在 Linux 虚拟化环境中。宿主机和容器资源采集结果不等同于生产 Linux 服务器，不能只在本地验证后就认为生产采集正确。

### 5.3 Compose 组织

建议保留现有应用 Compose，新增监控扩展 Compose，以同一 Compose 项目组合启动。最终文件组织在开发计划中确定。

要求：

- 明确 Compose 项目名、环境变量来源、相对路径解析与网络归属。
- 不创建第二套无意重复的应用、数据库或 Redis 服务。
- 本地与生产复用监控主体配置，端口、密码、域名和保留策略按环境区分。
- 保持原有业务流量入口和数据库、缓存连接方式，除非实施中发现必要变更并说明。
- 网络或挂载变更若导致业务容器重建，应提前在部署说明中明确影响。

### 5.4 容器通信

- 同一 Docker 网络内优先使用服务名或网络别名通信。
- Grafana 数据源地址指向 Prometheus 服务，而不是 Grafana 容器自身的 `localhost`。
- Prometheus 采集目标指向应用可达的指标端点，而不是 Prometheus 容器自身的 `localhost`。
- 内部通信不应依赖公网地址，也不要求通过 Caddy 转发。
- 服务器实际 Docker 网络名称及已有 Caddy 网络模式在实施前核对。

## 6. 应用指标需求

### 6.1 指标端点

- 提供符合 Prometheus 暴露格式的指标端点，建议路径为 `/metrics`。
- 具体采用现有 HTTP 端口上的受保护路由，还是独立内部监听端口，由开发计划根据安全性和现有架构确定。
- 指标端点不替代 `/health`。
- 默认不对公网开放；应明确经过 Caddy 时的限制方式。
- 指标接口自身的请求不计入业务 HTTP 指标；健康检查等内部路径也应明确排除，避免污染看板。

### 6.2 一期建议指标

| 类别 | 指标需求 | 口径要求 |
| --- | --- | --- |
| HTTP 请求量 | 累计请求次数 | 可按方法、路由模板、状态码聚合 |
| HTTP 错误率 | 根据请求计数计算 | 默认区分 4xx 和 5xx，不将两者混为一种错误 |
| HTTP 耗时 | 请求耗时直方图 | 明确单位、桶边界及记录时机，支持 P50/P95/P99 查询 |
| HTTP 并发 | 正在处理的请求数 | 请求结束、异常或取消后正确归还 |
| Go 运行时 | Goroutine、GC、内存等标准指标 | 优先复用成熟客户端能力 |
| 进程状态 | 支持平台上的 CPU、常驻内存、启动时间等 | 不与整台服务器资源指标混淆 |
| 采集状态 | 由 Prometheus 提供目标抓取状态 | 看板明确其含义为指标端点可采集性 |

以上为需求类别，不提前固定最终指标名称；实施时需形成指标字典，记录名称、类型、单位、标签、更新时机及计算口径。

### 6.3 流式请求语义

项目涉及流式请求，必须避免将长连接持续时间误认为普通接口响应延迟。

- 明确请求总耗时是从请求进入到处理结束，而不是到首个响应字节。
- 普通请求和流式请求应能够合理区分；具体分类方法在设计中确定。
- 流式请求开始响应后，后续业务失败可能不能改变 HTTP 状态码，因此 HTTP 2xx 不等于业务一定成功。
- 一期若只提供 HTTP 层指标，需在指标字典和看板说明中清楚标注这一限制。
- 首字节时间、首 Token 时间、流式中断率等业务指标不自动包含在一期范围中，需后续单独定义。

### 6.4 标签与隐私

- 路由标签使用路由模板，不直接使用包含动态 ID 的完整 URL。
- 不使用 API Key、访问令牌、请求正文、邮箱、请求 ID 等作为标签。
- 默认不以用户 ID、账号 ID 等无界增长维度作为标签。
- 未匹配路由应归入有界的统一类别，不能把任意访问路径转换为新标签值。
- 标签组合和耗时桶数量应受控，避免时间序列数量持续失控。

## 7. Prometheus 需求

- 自动加载版本管理中的采集配置。
- 能采集自身及 Sub2API 指标；自身指标用于辅助排障，不等同于外部可用性监控。
- 采集间隔、超时、数据保留时长及容量限制可配置。
- 建议以 15～30 秒作为初始采集间隔候选值，最终结合服务器资源确定。
- 数据目录配置持久化卷。
- 配置更新必须有明确生效步骤，如安全重载或重建对应容器，不能假设文件改变就会自动生效。
- 发布前支持配置语法检查；若引入规则，也应校验规则。
- 生产环境默认不向公网暴露管理和查询接口。

## 8. Grafana 需求

### 8.1 自动配置

- 通过 provisioning 自动创建 Prometheus 数据源。
- 通过 provisioning 自动加载项目基础看板。
- 数据源和看板使用稳定 UID，避免更新后出现重复对象或引用失效。
- 基础看板无需逐个环境手动导入。
- 仓库管理的看板应有明确归属，避免与用户自行创建的看板混淆。

### 8.2 一期基础看板

建议至少展示：

- 指标采集目标状态。
- 总请求速率和按路由聚合的请求速率。
- 4xx、5xx 速率或比例。
- 请求耗时 P50、P95、P99，并说明流式请求口径。
- 当前正在处理的请求数。
- Go 运行时与应用进程资源指标。

看板要求：

- 支持时间范围选择和刷新间隔配置。
- 明确指标单位、统计窗口和比例含义。
- 无请求或无样本时，不将“无数据”误标为“正常”。
- 分母为零的错误率等计算应合理处理。
- 延迟分位数基于直方图正确聚合，不直接平均不同分组的分位数。

### 8.3 面板迭代流程

- 允许在本地 Grafana 页面中探索和调整看板。
- 页面修改不会自动写回 Git，需要导出并更新仓库中的看板定义。
- 发布的正式基础看板以仓库文件为准。
- 明确 provisioned 看板能否在页面保存，以及文件更新覆盖页面修改的行为。
- 导出内容不应包含密码或只在开发环境有效的硬编码地址。
- 数据源通过稳定引用解析，避免生产环境重复手工修复。

## 9. 配置、数据与版本管理

| 内容 | 是否纳入 Git | 要求 |
| --- | --- | --- |
| 应用埋点和指标接口 | 是 | 与应用代码一起审查、测试 |
| Compose 与非敏感默认配置 | 是 | 可重现环境 |
| Prometheus 采集配置与规则 | 是 | 可校验、可回退 |
| Grafana provisioning 与看板 JSON | 是 | 自动加载、稳定引用 |
| 密码、令牌及其他密钥 | 否 | 使用环境变量或受控密钥文件 |
| Prometheus 历史指标 | 否 | 持久化卷保存，按保留策略管理 |
| Grafana 运行数据库 | 否 | 持久化保存，正式基础看板仍以 Git 为准 |

其他要求：

- Prometheus、Grafana 及新增采集器使用明确镜像版本，避免生产依赖浮动 `latest`。
- 指标名称、标签或直方图桶发生变化时，应同步评估查询和看板兼容性。
- 发布记录能够识别应用版本与对应监控配置版本。
- 如果支持多版本升级，应说明新看板面对旧指标、旧历史数据时的表现。

## 10. 安全、性能与可靠性

### 10.1 安全

- 生产 Grafana 禁止依赖公开默认密码，默认不启用匿名访问。
- 初期生产访问建议采用 SSH 隧道；若采用公网域名，需配置 HTTPS 和认证保护。
- 本地调试端口默认优先绑定 `127.0.0.1`。
- 指标接口、Prometheus 和 Exporter 默认仅内部可达。
- 在应用主端口暴露 `/metrics` 时，必须验证现有反向代理不会无意将其公开。
- 采集器遵循最小权限，不为方便而默认授予不必要的特权或 Docker Socket 访问。

### 10.2 性能

- 应用指标采集不应同步调用 Prometheus 或 Grafana，不应依赖监控服务可用性。
- 不在每次抓取时执行无界数据库扫描或高开销业务查询。
- 指标开销应通过测试或基准记录，避免显著影响吞吐、延迟与流式传输。
- 监控组件需配置或明确建议资源预算，具体额度结合服务器规格确定。
- 历史数据保留受控，避免耗尽业务服务器磁盘。

### 10.3 可靠性与更新

- 监控容器停止时，业务接口仍能正常处理请求。
- 监控与业务共享服务器资源，并非完全故障隔离；需通过资源和磁盘策略降低相互影响。
- 重启、升级时保留持久化卷。
- 监控配置更新不要求无关业务服务全部重启。
- 回退监控配置应有文档步骤；跨监控软件版本回退时，不假定数据格式天然兼容。
- 日常发布流程不得使用删除数据卷作为默认步骤。

## 12. 验收标准

### 12.1 本地启动与自动配置

- 使用文档中的命令可启动应用依赖及两个监控容器。
- 无需手工创建数据源或导入基础看板即可查看监控。
- Prometheus 中应用目标可正常采集。
- 不启用监控时，原有开发启动流程仍可使用。

### 12.2 指标正确性

- 发送已知数量请求后，对应计数增量符合预期。
- 通过受控测试或测试环境验证 4xx、5xx 能被正确区分，不要求破坏真实业务制造故障。
- 耗时指标类型、单位、桶与查询一致。
- 请求完成、异常和取消后，并发指标不持续泄漏。
- 动态 URL 和任意未匹配路径不会导致无界标签增长。
- 指标端点和约定排除的健康检查请求不会污染业务请求统计。
- 中间件不破坏流式响应的及时输出及取消处理。

### 12.3 看板与版本迭代

- 请求量、错误率、耗时、并发和运行时指标均可展示。
- 无数据与正常零值能够合理区分。
- 本地修改看板、导出并提交文件后，新环境能自动加载同样的基础看板。
- 更新后无重复数据源、重复基础看板或失效引用。
- 仅更新监控配置时，无需重新构建应用镜像，除非同时修改了应用埋点。

### 12.4 持久化、安全和故障隔离

- 在不删除数据卷的前提下重建监控容器，历史数据和必要配置仍保留。
- 生产部署后，公网不能未经授权访问应用指标端点或 Prometheus。
- Grafana 按约定的认证与访问方式开放。
- 停止 Prometheus 或 Grafana 后，应用核心请求仍正常执行。
- 配置保留策略，并记录服务器资源占用验证结果。

### 12.5 生产部署

- 在现有应用部署上完成监控接入，不重新初始化业务数据库或缓存。
- 实际 Docker 网络与采集地址经过验证。
- 更新后 Grafana 能展示服务器产生的新指标。
- 若包含宿主机或容器资源采集器，应额外在生产 Linux 环境验证数据语义和权限。

## 13. 风险与约束

| 风险 | 应对要求 |
| --- | --- |
| 生产部署配置与仓库示例不一致 | 实施前核对 Compose、网络、挂载和镜像版本 |
| 本地与生产网络寻址不同 | 通过环境配置隔离差异，避免硬编码 |
| macOS Docker 资源指标与 Linux 不同 | 应用指标本地验证，系统指标生产补验 |
| 流式长请求造成延迟误读 | 明确 HTTP 总耗时与首响应、业务成功的区别 |
| 标签高基数造成内存和磁盘增长 | 限制标签维度，使用路由模板 |
| 看板只保存在 Grafana 页面 | 正式看板导出并进入 Git |
| 新指标与旧看板不兼容 | 应用和看板联动发布、记录兼容性 |
| 监控数据占满磁盘 | 设置保留和容量策略，记录容量规划 |
| Caddy 意外公开指标接口 | 明确路由限制并从外部验证 |
| 同机监控无法观察整机宕机 | 接受一期限制；如有需要后续增加异机探测 |

## 14. 制定开发计划前需确认的事项

以下事项不阻止需求文档形成，但会影响开发范围和部署设计：

1. 一期是否采用本文建议的“应用指标闭环”，还是同时必须包含服务器、容器、PostgreSQL 或 Redis 监控？
2. 第一版看板是否仅需通用 HTTP 和运行时指标，还是必须包含特定业务、上游调用或流式首响应指标？
3. 生产服务器 CPU、内存、剩余磁盘，以及可分配给监控系统的资源预算是多少？
4. 生产实际使用的 Compose 文件、启动命令和发布流程是什么？
5. Grafana 初期通过 SSH 隧道访问，还是需要独立域名与 HTTPS？
6. 本地与生产分别需要保留多少天的指标？生产磁盘容量上限是多少？
7. 一期是否必须提供通知告警？如需要，通知渠道及告警对象是什么？

未确认前，建议开发计划按以下基线估算：

- 一期聚焦 Prometheus、Grafana 和应用基础指标，不默认加入所有 Exporter。
- 本地以完整 Docker 环境为联调基线。
- 基础看板独立运行在 Grafana，不嵌入现有业务前端。
- 数据源和看板采用 provisioning，正式配置以 Git 为准。
- 告警通知和业务细分指标作为后续迭代，除非用户明确提升为一期要求。
